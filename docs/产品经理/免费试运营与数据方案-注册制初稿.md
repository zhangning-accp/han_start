# 青禾街免费试运营与数据方案

2026年11月7日。供负责人确定试运营节奏、安排下一版开发和验收运营数据使用。

已确定：面向越南、印尼、巴西开展 1–3 个月免费试运营，收集注册、活跃、反馈、使用时间段与时长，并按国家分类统计。本轮只确定方案，不开发账号或统计后台，不开启新数据采集，不部署服务。

本方案的指标定义、默认周期和实现顺序作为下一版开发建议。目标是用同一套可核对的数据，判断各国用户能否顺利开始、是否持续使用、在哪些地方受阻，以及哪些内容值得继续投入。

## 免费期和复盘节奏

建议按全站最长 90 天设计，以首次正式对外开放之日为起点，实际起止日期可配置；不是每位用户注册后重新获得 90 天。第 30、60、90 天分别复盘。未确定正式开放日期前，不显示虚构的倒计时或自动开始计时。

免费期不要求绑卡、不自动续费或扣费。后续是否收费、收费范围和实施日期另行决定并提前说明。免费范围以页面列出的可用功能为准，AI 如有次数限制应明确显示，不能宣传为无限调用。

| 阶段 | 主要工作 | 复盘时要回答的问题 |
| --- | --- | --- |
| 开放前 | 核对注册、身份合并、数据口径、母语说明、海外手机访问和账号权限 | 数据是否可信，用户能否完成首次体验 |
| 第 1–30 天 | 小批次招募，观察新手村完成与流失，优先修复阻碍使用的问题 | 哪国、哪个渠道的用户最容易开始使用 |
| 第 31–60 天 | 在稳定版本上观察回访、章节推进和重复反馈 | 什么内容和帮助方式能让用户再次使用 |
| 第 61–90 天 | 检查较长期留存、运营成本及不同国家的表现 | 下一阶段重点服务谁，优先投入什么 |

三个国家可以同时收集数据，但须记录各自的开放日期、招募来源和人数。国家间比较同时展示人数与比例，并按注册批次和渠道拆分，避免把招募方式不同造成的差异归因于国家。样本少时看具体使用过程与反馈，不因一两位用户的变化宣布某个市场胜出。

## 用户身份和国家分类

建议允许游客先体验，在保存跨设备进度或继续体验时完成注册；确切出现位置须用首次体验观察验证。账号验证方式在开发账号模块时确定，优先选稳定、低操作负担的方式。注册成功必须由服务端确认，并形成稳定的账号 ID。

注册人数按成功注册的账号去重，不把刷新页面、登录次数、邮箱验证失败或浏览器随机编号算作新注册。同一账号跨设备登录计一个账号；账号数仍不等于经过真人身份核验的人数。游客独立访客单独展示，以浏览器匿名 ID 估算，并标注换设备、清除数据可能重复计数。

游客转注册后，在获得相应授权并确认身份关联时合并其体验记录，保留每条事件 ID，避免同时计为两个用户。现有本地存档由用户主动关联到账号；旧事件缺少统计所需字段，不能补造成真实注册或历史活跃记录。

| 分类字段 | 取得方式与用途 |
| --- | --- |
| 通常居住国家或地区 | 用户自行选择；越南、印尼、巴西分别展示，其他及未提供单独分组，不依靠辅助语言猜测 |
| 注册时国家 | 注册时的国家快照，用于注册批次与留存比较；后续修改资料不改写旧批次 |
| 事件发生时国家 | 当时用户填写的国家快照，用于活动、时长、反馈分组；不表示精确物理位置 |
| 辅助语言 | 越南语、印尼语、巴西葡语、英语、中文，独立于国家记录 |
| 起步难度 | 零基础、句式帮助、自由输入，记录当时设置；与用户自报汉语基础分开 |
| 汉语基础与学习目的 | 可选短问卷，支持跳过；用于比较零基础、已有基础以及旅行等需求 |
| 来源渠道 | 受控推广链接或用户自报，如教师推荐、社群、自然访问；未识别来源保持未知 |
| 设备与版本 | 手机或电脑、操作系统类别、产品版本；不用设备指纹识别用户 |
| 时区 | 浏览器提供的 IANA 时区，可由用户纠正；缺失或无效时不猜测当地时间 |

首次进入只保留必要信息和简短的数据用途说明。学习目的、评价、详细背景等分时收集，避免一次问卷妨碍进入新手村。

## 核心指标定义

全站趋势报表建议默认使用 UTC 自然日，界面和导出明确标注时区、日期范围与统计口径。国家对比沿用同一报表时区，筛选变化不应暗中改变日界线。

以下是青禾街建议采用的产品口径，不直接照搬某个分析工具的默认定义。

| 指标 | 计算口径 | 帮助判断 |
| --- | --- | --- |
| 新注册账号 | 所选日期内服务端首次注册成功的非测试账号去重数 | 用户增长 |
| 累计注册账号 | 截至所选结束日的注册总量；已删除账号的历史处理须单独标注，不能与当前有效账号混称 | 累计规模 |
| 当前有效账号 | 截至所选结束日未注销、非测试的已注册账号数 | 可服务的账号规模 |
| 游客独立访客 | 日期范围内匿名浏览器 ID 去重数，与注册账号分开显示 | 注册前访问情况 |
| 注册转化 | 选定首次访问批次中，在首次访问后 7 天内注册的去重访客数 ÷ 该批次符合采集条件的去重访客数；仅计算观察窗口已满者 | 入口到注册的转化 |
| 日活 DAU | 同一 UTC 日内至少完成一次有效产品交互的注册账号去重数；游客活跃单列 | 真正使用产品的人数 |
| 周活与月活 | 截至所选日期，最近 7 天或 30 天内有有效产品交互的注册账号去重数；明确是滚动窗口 | 使用覆盖面 |
| 首次体验激活率 | 新注册批次中，注册后 24 小时内完成新手村且成功保存作品的账号比例；已在游客阶段完成且成功关联的用户视为注册时已激活 | 用户是否获得第一次完整体验 |
| 新手村步骤完成 | 进入每一步、完成每一步、跳过的人数；同一账号在同一批次内去重，另记实际重试次数 | 哪里卡住或退出 |
| 第二章进入和完成 | 完成新手村后 7 天内进入夜市的比例，以及夜市各步骤完成情况；观察未满者单列 | 引导后的继续使用 |
| D1 D7 D30 留存 | 注册日为 D0，同一账号在第 1、7、30 个 UTC 自然日发生有效产品交互的比例；这是指定日回访，不是期间任意一天回访 | 是否持续使用 |
| 有效使用时长 | 前台可见、页面有焦点且近期有交互的累计时间，排除明确空闲与后台停留 | 用户实际投入 |
| 人均每日有效时长 | 当日有效交互产生的去重使用区间总时长 ÷ 当日活跃账号数，同时显示中位数 | 典型用户使用深度 |
| 会话次数与时长 | 连续使用视为一个会话；连续 30 分钟没有有效交互则结束，再次使用形成新会话。展示总会话数、每人会话数和每次有效时长 | 一天使用几次、每次多久 |
| 当地使用时间段 | 按用户当时的时区转换为星期和小时，分别展示活跃账号数与有效分钟数 | 各国用户常在什么时候使用 |
| 意见反馈 | 提交数、去重提交账号数、分类、状态、首次处理时间、处理完成时间和评价分布 | 用户遇到了什么，以及是否得到处理 |
| 运行质量与成本 | 主要请求失败率、页面错误、AI 请求量和实际可得的用量；有真实账单后再计算人均成本 | 免费运营能否稳定持续 |

“有效产品交互”首版建议限定为主动执行学习或建造动作：选择问候或饮料、提交练习、明确点击继续、放置或编辑组件、成功保存作品。仅打开页面、登录、切换语言、后台心跳、查看后台、管理员审核不计入产品 DAU。反馈提交人数另列，避免把只来报告故障的人当成正常使用。

活跃人数、时长和留存的默认对象都是非测试注册账号。游客报表独立显示；提供全体已知使用者报表时，须在身份合并后去重，不能直接相加游客与账号两张表。

注册转化、24 小时激活率、7 天内进入第二章等带观察窗口的比例，均只使用窗口已完整结束的批次计算正式结果；仍在观察的账号另列数量。每个比例旁展示分子与分母，避免只给一个百分比。

国家趋势使用事件发生时国家，因此同一账号在一段时间内修改国家后，可能出现在不同国家的期间去重数中。全站总数重新去重，不直接把国家行相加。注册转化和留存使用固定注册批次及其国家归属，并明确标注。

## 时间与留存的计算边界

用户打开页面一小时，不等于学习一小时。建议首版使用如下规则估计有效时长：页面可见且有焦点，从一次真实用户交互开始计时；离开页面、切换后台时立即暂停；最后一次交互超过 60 秒则按空闲处理，再次交互后恢复。长时间静止阅读可能被低估，因此后台应标注为估算有效时长，同时展示任务完成与重试，不能用时长代表学习效果。

前台可见与有焦点是主流参与时长统计的重要基础；青禾街增加的 60 秒空闲阈值属于本产品拟定的规则。[Google Analytics 对参与时长的说明](https://support.google.com/analytics/answer/11109416)

实施时建议每 15 秒增量记录一次有效区间，离开页面时尝试补报。标签页重复打开、请求重试及跨设备区间重叠不得重复累加；服务端对同一账号的重叠区间取并集。关闭浏览器来不及上报时允许出现少量缺失，不根据最后一次打开时间虚构余下时长。断网补报要保留实际发生时间和接收时间，对异常时钟与过长区间做校验。

事件统一存 UTC 时间，同时保留经校验的时区用于当地时间分析。日趋势按 UTC 日界线拆分有效区间，小时热力图按用户当地小时边界拆分；不要把一整个跨午夜会话都算到开始当天。印尼和巴西不能仅凭国家套用一个固定当地时区。

留存采用明确的开始事件和返回事件，以相同条件对比各批用户；这种定义方式与通用产品留存分析一致。[PostHog 留存定义与分组说明](https://posthog.com/docs/product-analytics/retention)

例：某注册批次有 10 个合格账号，其中 3 个在第七个自然日有有效交互，则 D7 为 3/10，即 30%。注册尚未满相应观察窗口的账号显示“观察中”，不能记为未留存。汇总多个注册批次时，用全部符合观察条件的账号作为分母，不直接平均各批次的百分比。当天未结束的趋势及尚在补报的数据标为暂定。

## 意见收集和处理

所有章节提供常驻反馈入口，允许使用自己的辅助语言填写。新手村完成时可展示一次可跳过的短问题，例如“刚才最难的地方是什么”；避免每一步弹窗索要评价。

建议分类：操作不明白、中文太难、翻译问题、程序故障、功能建议、其他。可选填写满意度和是否希望被联系。联系方式单独保存并限制访问，不把用户提交反馈视为订阅营销消息。

反馈自动关联提交时的国家、辅助语言、难度、章节步骤、产品版本与时间；保留用户原文。若后续加入翻译，原文与译文并存，译文标明来源。不要默认采集聊天全文、键盘输入过程、录音或屏幕录像。

后台状态建议为“待查看 → 已分类 → 处理中 → 已解决”，另有“不处理”状态并记录原因。每条反馈保留负责人、处理时间和关联版本，支持按国家、分类、严重程度和状态筛选。反馈接收由服务端确认，重复发送不生成多份。用户应能查看自己提交的反馈与处理状态。

## 最小数据记录和访问范围

优先采用业务事件白名单。记录完成某个动作，而不是全量收集每次点击和所有输入。建议事件包含唯一事件 ID、匿名或账号 ID、事件类型、发生时间、接收时间、会话 ID、国家快照、辅助语言、难度、场景步骤、产品版本、来源渠道及数据说明版本。注册、保存成功等事件由服务端确认；操作尝试和失败须分开记录。

学习数据应继续区分有帮助与无帮助完成，不能把点词过关宣传为独立语言能力。既有测试身份、管理员身份、演示事件和自动测试事件须明确标记并默认排除；现有 QA 历史不回填到正式试运营统计。

首次采集前，以所选辅助语言说明收集内容、用途、保存期限和管理方式。必要业务记录与可选行为分析分别处理；可选分析应能关闭。后台同时展示采集覆盖情况，不能把未参与分析的人算成“没有活动”。具体上线地区的数据要求在部署方案确定后核对。

原始行为记录建议保留 120 天，覆盖最长 90 天试运营和随后 30 天复盘；之后删除或按已说明的方式汇总，不以无限期保存作为默认值。账号资料和反馈设定各自保留规则。提供个人数据导出和删除能力，明确删除后明细及历史汇总的处理方式；不能让前台声称已删除而后台仍可查询到对应个人记录。默认运营看汇总，账号联系方式和反馈原文仅向有需要的管理角色开放。

## 与当前版本的差距

当前 v0.3 是本机原型：浏览器随机 ID 用于本地体验隔离；学习记录和私人反馈主要保存在浏览器；服务端保存作品、投稿、审核与部分操作记录。现有这些能力不能直接称为正式账号注册、集中运营分析或可对外使用的管理后台。

下一版须先补稳定账号与数据存储，再接事件记录、时长计算及运营查询。当前页面关于“学习记录仅在浏览器”“私人反馈仅本机保存”的说明，应在相应行为真正改变时同步更新全部辅助语言。旧版本不会因本方案自动开始上传。

## 开发顺序和验收条件

| 顺序 | 交付范围 | 关键验收 |
| --- | --- | --- |
| 第一批 | 账号、国家与语言资料、数据说明、管理员访问边界 | 注册幂等、身份验证、跨设备同账号、游客关联不重复、旧存档不丢失、普通用户无法进入后台 |

方案定稿后的首个开发重点是“可信注册数、可信日活、按国家查看、有效时长和反馈能够到达后台”。留存与路径分析所需事件应从正式试运营第一天开始记录，避免后期补看板时缺失历史。收集到数据后，每周结合实际反馈做一次产品取舍，第 30、60、90 天评估是否扩大招募及下一阶段方向。
